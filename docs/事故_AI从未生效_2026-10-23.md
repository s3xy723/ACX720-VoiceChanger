# 事故复盘：AI 分离从未真正生效（2026-10-23）

一句话：**「分离 × 计算机本地模型」在打包版里 100% 静默降级成纯 DSP 中置提取，
demucs 一次都没跑过。** 前面几轮针对"AI 分离效果"的所有调参，全都作用在一条
根本没被执行的代码路径上。

---

## 1. 故障链

```
host_app.py import
    ↓
import ai_separate            ← 模块本身很轻（numpy/threading），没问题
    ↓
HAVE_AI, AI_WHY = ai_separate.available()
    ↓
available() 里 __import__("torch")
    ↓
✗ ModuleNotFoundError（打包版没带 torch）
    ↓
HAVE_AI = False，并且**此后永不刷新**
    ↓
_split_worker: use_ai = (engine == LOCAL_MODEL and HAVE_AI and ...)
    ↓
False → 走 else 分支：vocal_split.VocalSplitter（中置提取 + 谐波梳）
    ↓
只在日志里留一行"提醒：选了「计算机本地模型」但 ... 按纯 DSP 中置提取跑"
```

### 为什么 packaged 版必然失败

轻量版 EXE 刻意**不打包** torch（打包会变成 4.8 GB），torch 是运行时由
`local_ai.ensure_local_runtime()` 从用户级 site-packages
（`%APPDATA%\Python\Python312\site-packages`）**挂进 sys.path** 的。

而 `available()` 是在 **host_app import 阶段**被调用的 —— 那一刻
`ensure_local_runtime()` 还没运行，sys.path 里没有 torch，import 必然失败。

### 为什么之前"看起来是好的"

- `--ai-check` 走的是 `local_ai.demucs_ready()` → 内部先 `ensure_local_runtime()`
  再探测，所以**能通过**。自检通过 ≠ 主流程用了 AI。
- 界面上的「本地 AI 环境」标签由后台线程 `local_ai.probe()` 填，它同样会先挂载，
  所以显示"demucs 可用 / CUDA 可用"。**显示可用 ≠ 主流程用了 AI。**
- 只有 `_split_worker` 那一处用的是 import 时冻结的 `HAVE_AI`。

## 2. 复现方式（两行）

```python
import sys
sys.path = [p for p in sys.path if "Roaming" not in p]   # 模拟打包版：torch 还没挂
import host_app
print(host_app.HAVE_AI)          # 旧代码: False  ← 主流程据此跳过 AI
print(host_app.local_ai.demucs_ready())   # (True, '')  ← 其实完全可用
```

## 3. 修复

| 位置 | 改动 |
|---|---|
| `host/ai_separate.py::available()` | 先 `import local_ai; local_ai.ensure_local_runtime()`，再 `__import__("torch")`。挂载只在第一次真正需要时发生 |
| `host/host_app.py` import 段 | **不在 import 阶段判定**。`HAVE_AI` 只留作"未检测"占位，实际判定交给 `_ai_ready()` |
| `host/host_app.py::_ai_ready()` | 新增。第一次调用时现查（会挂 torch，几秒），**只缓存成功**；失败不缓存，用户后来装好 torch 不用重启 |
| `host/host_app.py::_split_worker()` | 引擎选了本地模型时先 `_ai_ready()` 现查；进度条显示"检查本机 AI 运行时…" |
| 降级提示 | 从"一行日志"升级为**写进完成信息**：`engine="中置提取 + 谐波梳（⚠ AI 未启用：原因）"` |
| AI 分支 engine 文案 | 改成 `demucs（high 档）+ 左人声/右伴奏`，一眼能看出走的是哪条 |

## 4. 回归测试

`host/test_host.py::test_ai_gate`（3 条断言）：

1. **负对照**：把 `available()` 打桩成 `(False, "模拟：没装 torch")`，
   必须返回不可用且把原因带出来 —— 防"硬编码成 True"。
2. 把 `HAVE_AI` 置为 `False`（模拟打包版的 import 结论）后，
   `_ai_ready()` **仍须**判成可用 —— 这条正是本事故。
3. 可用之后走缓存，不重复挂载。

验证过它会 FAIL：把 `_ai_ready()` 改回 `return bool(HAVE_AI), AI_WHY`，
整轮测试变成 **3 FAIL**；改回来即 **116 PASS / 0 FAIL**。

## 5. 这件事的教训

- **"依赖可用"和"功能被执行"是两件事。** 自检、状态灯、日志提示都只证明前者。
  判断后者只能靠一条**能 FAIL 的断言**，比如这次：把 import 时的结论强行置为
  False，功能仍须工作。
- **不要在 import 阶段判定运行环境。** 运行时才准备好（vendoring / 动态挂载 /
  lazy import）的东西，一律推迟到"真正要用"的那一刻，并且失败不要永久缓存。
- **静默降级是最坏的失败方式。** 降级本身没错（缺依赖不能崩），但必须让人在
  **结果**上看得见（这次改成了写进完成信息），否则会拿 A 的结果评价 B。
- **先证明路径被执行，再优化路径。** 前几轮全部违反了这一条。
