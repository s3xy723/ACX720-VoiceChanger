# AI 处理卡在 100% 的修复（2026-10-20）

## 现象

文件模式选「分离 × 计算机本地模型（demucs）」，处理进度到 100% 后
界面一直不动，按钮不恢复，也不报错。

## 原因

`_proc_worker` / `_split_worker` 在**工作线程**里直接调用 Tk：

- `self.after(0, ...)`（demucs 进度回调，每秒几十次）
- `self._log(...)`（变调、峰值归一化等）

Tkinter 不是线程安全的。demucs 的进度回调频率一高，Tcl 解释器的锁被
工作线程抢住，主线程拿不到锁；表现就是：

- 进度停在 100%
- 窗口还能动一点，但回调永远不执行
- 有时弹出 `RuntimeError: main thread is not in main loop`

## 修复

1. `App.__init__` 增加线程安全队列 `self._ui_q`。
2. 新增 `_post(fn, *args)`：工作线程只把回调塞进队列，不碰 Tk。
3. 主线程 `_poll()` 每 50 ms 调 `_drain_ui()`，从队列取出执行。
4. 工作线程里所有 `self.after(0, ...)`、`self._log(...)` 改成 `_post(...)`：
   - demucs 进度
   - 中置提取进度
   - 文件变调进度
   - 处理完成 / 失败
   - 音轨写出失败
   - AI 环境准备状态
5. 写文件阶段增加提示：`正在写输出文件…` / `正在写人声 / 伴奏音轨…`，
   避免看起来又卡在 100%。

## 验证

源码线程化实测（5 秒音频，demucs）：

```
elapsed 2.35 processing=False proc=(240000, 2)
state=完成 out.wav 用时 2.29 秒（2 倍实时）
分离：demucs + 左人声/右伴奏
```

不再出现 `main thread is not in main loop`，进度能正常走到「完成」。

重新打包后的 EXE：

```
dist/ACX720VoiceChanger/ACX720VoiceChanger.exe --selftest
RESULT: ALL PASS
```

## 附：`PermissionError(13, 'Permission denied')`

2026-10-20 22:14 实测另一个失败：

```
22:13:05 分离完成
22:13:48 写回失败
22:14:02 处理失败: PermissionError(13, 'Permission denied')
```

输入在 `D:\QQFile\...flac`，输出写 `D:\QQFile\..._变声.wav`。
目录本身可写，但 Windows 上 QQ 接收目录、Defender 扫盘、播放器占用
都会让 `sf.write` 偶发 `PermissionError(13)`。

已加写入重试：

- 失败后按 0.4/0.8/1.2… 秒重试，最多 6 次；
- 仍失败则改存成 `原文件名_时分秒.wav`，不再直接报错；
- 人声/伴奏两条音轨同样走这个重试；
- 失败弹窗现在会带输出路径和“关掉占用文件的程序/换输出目录”的提示。

如果还报 PermissionError：

1. 关掉正在播放该 wav 的播放器、QQ 预览、剪辑软件；
2. 输出目录换成本地非同步目录（如 `D:\ACX720_输出`）；
3. 再点开始处理。

## 如果还卡

- 确认用的是 2026-10-20 22:17 之后重新打包的 EXE；
- 看界面底部日志最后一行：
  - `正在写输出文件…` → 磁盘/路径慢，换本地盘；
  - `正在写人声 / 伴奏音轨…` → 三份大文件写入，等一会儿；
  - `...被占用/拒绝写入，改存：...` → 已经自动换名成功；
  - 没有任何新日志 → 把日志文本发我。
