# 文件变声：permission denied 与连续爆音 —— 定位与修复（2026-10-22）

> 结论先行：两个现象**都不是**通常以为的那个原因。
> - permission denied：不是"有程序占用"，而是**下拉框里混进了根本打不开的 WDM-KS 设备**，
>   外加**播放器拿文件自己的采样率去开流**（WASAPI 卡只吃自己原生采样率）。
> - 连续爆音：不是"缓冲太小/回调被拖慢"，而是 **MCU 把有符号样值按 `& 0x0FFF` 取模
>   送进了 12 位 DAC**，负半周翻到满量程，输出变成折叠锯齿。
>
> 全程没有改动任何变声处理逻辑（`dsp_core` / `StereoChain` / 参数含义一律未动）。

---

## 1. 先说关键的排错结论：两个"常识"在本项目里都不成立

| 常见怀疑 | 本机实测 | 结论 |
|---|---|---|
| 缓冲太小 → underrun 爆音 | 播放 3 s / 143 次回调，**欠载 0、过载 0** | 排除 |
| 分块处理有块边界瑕疵 | 分块 8192 与整段一次处理**逐样本完全相同**（差异 0.0e+00） | 排除 |
| 增益/重采样溢出削波 | 输出 最大 0.5998，**削波样本 0**，相邻最大跳变 0.044 | 排除 |
| 同一设备被重复打开 | 同一 WASAPI 设备连开两条流 **都成功**（共享模式允许） | 排除 |
| 文件被别的进程锁着 | 占着句柄再 open **照样成功**（Windows 读共享） | 排除 |
| **WDM-KS 设备打不开** | 17 个输出里 **6 个**、15 个输入里 **7 个**必然失败 | ★ 主因 1 |
| **44.1 kHz 在 WASAPI 卡上开不了流** | `Invalid sample rate`（dev 14/16 都拒，MME 的 dev 4/11 收） | ★ 主因 2 |
| **MCU 的 `& 0x0FFF` 取模** | 440 Hz 正弦 → 主峰跑到 **8134 Hz**，失真比主音高 **9.1 dB** | ★ 爆音真凶 |

## 2. permission denied 的根因与定位

### 2.1 根因 A：设备列表混进了打不开的 WDM-KS 条目

`audio_io.list_devices()` 把 PortAudio 枚举到的设备**全列出来**，但 Windows 上
WDM-KS 那一批**一条都开不了**：

```
dev=20  Headphones 1 (Realtek HD Audio 2nd output with HAP) [Windows WDM-KS]  FAIL
dev=24  Speakers 1 (Realtek HD Audio output with HAP)       [Windows WDM-KS]  FAIL
dev=31  Speakers (VB-Audio Point)                           [Windows WDM-KS]  FAIL
```

报错是 `Unanticipated host error [PaErrorCode -9999]`；在部分驱动/语言环境下就显示成
**"permission denied"**。名字都很正经（"Speakers 1 (Realtek HD Audio output with HAP)"），
用户自然以为选的是自己的扬声器 —— 于是"明明没人占用啊"。

### 2.2 根因 B：用文件的采样率去开流

`Player.play()` 是 `sd.OutputStream(samplerate=self.sr, ...)`，而 `self.sr` 来自
**文件本身**。WASAPI 设备通常只接受自己的原生采样率：

```
dev=14 扬声器 (Realtek) [WASAPI]   44.1 kHz → FAIL Invalid sample rate
dev=16 CABLE Input      [WASAPI]   44.1 kHz → FAIL Invalid sample rate
dev=11 扬声器 (Realtek) [DirectSound] 44.1 kHz → OK
dev=4  扬声器 (Realtek) [MME]         44.1 kHz → OK
```

**绝大多数音乐文件都是 44.1 kHz** → 稳定复现。而且 MME 那几张卡能开，表现为
"换一张卡就好了"，极难往采样率上想。

### 2.3 为什么不能用 `sd.check_output_settings()` 预筛

它对 WDM-KS **一律返回 OK**（实测 dev 20/21/24/25/29/31 全部 "OK"），只有采样率
这一项它是准的。所以设备可打开性必须**真开一次**才知道。

### 2.4 代码层面怎么定位"到底是哪一步、哪个资源"

埋点原则：**报错必须带上"谁被拒了"**，只打 `PaErrorCode` 无法定位。

- `player._dev_desc(device, sr)` 新加：输出
  `dev=16 CABLE Input (VB-Audio Virtual Cable) [Windows WASAPI] @ 48000 Hz
   （该设备原生 48000 Hz，不匹配会直接拒）`
- `Player.play()` 失败时打 `播放启动失败：%r\n  目标：%s`（原来是只有 `%r`）
- `host_app._enum_devices()` 把被剔除的设备逐条打进日志：
  `设备不可用已剔除（输出）：Speakers 1 ... [Windows WDM-KS] —— 该接口不支持共享模式打开`

## 3. 连续爆音/电流声的根因

`mcu/f103_spi_mcp4922/main.c` 原来：

```c
SPI2_DR = (uint32_t)(cmd | (d12 & 0x0FFFu));   /* d12 = FPGA 送来的 16 位样本 */
```

FPGA 送的是**有符号**补码（-32768..+32767），MCP4922 要的是 **0..4095 无符号**码。
`& 0x0FFF` 是**取模不是截断** —— 负半周被翻到接近满量程。

对 440 Hz 正弦的实测对比：

| | 相邻样本最大跳变 | 主峰 | 失真+噪声 / 主音 |
|---|---|---|---|
| 原 `& 0x0FFF` | **3223 / 4095** | **8134 Hz** | **+9.1 dB**（比主音还响） |
| 修好 `>>4` | 186 / 4095 | 440 Hz | 0.0 dB |

跳变超过满量程 3/4 的样本每秒 **20169 个** —— 这就是连续的"咔哒咔哒"加"电流声"，
而且内容几乎听不清。

# 第二轮（同日晚些时候）：残留杂音定位 + 输出文件彻底修好

## A. 输出文件报错 —— 已彻底修好（6/6 验收通过）

原来的 `_save_audio_retry` 只 catch `OSError`、且只把 `PermissionError` 当"可重试"，
于是下面三类错误**直接冒到界面上**变成"输出文件报错"：

| 触发 | 原来的报错 | 为什么兜不住 |
|---|---|---|
| 采样率读到 0 | libsndfile `Error: sampling rate not specified` | 不是 OSError |
| 目标目录不存在 | `FileNotFoundError` | 是 OSError 但不在可重试名单里 |
| 数据里有 NaN/Inf | libsndfile 报错 / 写出垃圾 | 不是 OSError |

改动（都在 `host/`）：

- `audio_io.norm_sample_rate(sr)` —— 采样率收敛成**正整数**，非法直接 `ValueError`
- `audio_io.sanitize_audio(data)` —— NaN/Inf 替成有限值并夹回 [-1,1)
- `audio_io.ensure_dir(path)` —— 写之前先建目录
- `save_wav` / `save_audio` 全面改用上面三个，**采样率/声道/位深显式定死**：
  采样率 = 同一个 int；声道 = 数据实际列数；位深 = 16 bit PCM
- `host_app._save_audio_retry` —— 先归一化采样率 + 建目录，再 catch **所有**异常重试，
  最后一次换带时间戳的备选文件名，仍失败才把原因报出来（不再静默吞掉）
- `host_app._do_process` —— **开工前**就校验并固定采样率，不再等写盘才发现
- `host_app._proc_worker` —— `sr = audio_io.norm_sample_rate(cfg["_sr"])`，
  处理 / 写盘 / 播放器用的是同一个值

验收（`tool/verify_file_module.py` 第 6 项）：

```

## B. 残留杂音 —— 定位到具体环节了

### B1. 变调算法本身会带来 5~9 dB 的调幅（**未改，属设计特性**）

双抽头 Hann 交叉淡化变调器（rtl/pitch_shift.v 的逐比特移植）两个抽头固定相距
1024 点，合成时两路相位不相关，输出幅度随相位差起伏。对纯音实测：

```
输入 220 Hz  : 包络起伏 4.8 dB
输入 440 Hz  : 包络起伏 8.9 dB     ← 最严重
输入 1000 Hz : 包络起伏 5.9 dB
```

听感就是"跟着声音一起出来的发毛/呜呜抖动"——**只在有信号时出现**，和用户的描述
完全吻合。这是该算法的固有特性（板子上的 RTL 也是这个行为），按"不改变声逻辑"
的要求**没有改动**。若想消除，只能换变调算法（比如相位声码器），那是另一个话题。

### B2. DAC 量化由截断改成四舍五入（**已改**）

`sample_to_dac()` 原为 `(v+32768) >> 4`（截断），会带来 -0.5 LSB 的系统性偏置，
且量化误差与信号**相关**（是跟着波形走的失真，不是白噪声），小信号时是沙沙声。
改成 `(v+32768+8) >> 4`。遍历全部 65536 个 16 位值，平均量化误差确实变小。

### B3. 一次失败的尝试：BUF 位改 1（**已回滚，记录在此免得再试**）

我一度以为 MCP4922 的 bit14 `BUF` 是"输出缓冲"，想靠它改善带载线性度。
**实测改完喇叭彻底不出声**（门控 ON/OFF 从 +37 dB 掉到 -5 dB）。
查证后确认：MCP4922 的 bit14 是 **VREF 输入**缓冲控制位，不是输出缓冲；
输出运放本来就是常开的。本板 VREF 直接接 VDD（低阻抗），开这个缓冲只会
改变基准通路。已改回 `BUF=0 / GA=1 / SHDN=1`（`0x3000` / `0xB000`），
代码里也写了注释。**别再动这个位。**

## C. 当前状态（需要人工确认的一件事）

写完这轮之后喇叭**没有声音**，但数字链路每一步都是通的：

```
FPGA 帧回显        1144/1144 = 100%
MCU 收字           ≈ 48.7k 字/秒（理论 2×24414 = 48,828）
g_ovr              0
g_last_word_ms     == g_ms（处于 PASS 直通，不是自检音）
SPI2_CR1           0x0B54      GPIOB_CRH 0xB4B34444

即：**声音数据确实送到了 DAC 门口**，剩下的是 MCP4922 → 两级 RC → PAM8403 → 喇叭
这段模拟链。请按顺序摸一遍：

1. PAM8403 板子**有没有上电**（这是最可能的，指示灯/5 V 有没有掉）
2. 喇叭接线、MCP4922 的 VOUTA/VOUTB 有没有脱焊/松脱
3. 万用表直流档量 VOUTA/VOUTB：静音时应 ≈ **1.65 V**（中点）；0 V 查 VREF/SPI，3.3 V 查样值
4. 手指碰 PAM8403 的 L IN / R IN：有"嗡"声 → 功放和喇叭是好的，问题在 DAC/RC
5. 1.5 V 电池碰喇叭两端：有"咔啦"声 → 喇叭好

（排查期间我用脚本往链路里灌过 30 秒直流，虽然输出有隔直电容、理论上不会烧，
但如果功放板有保护，也可能因此锁住 —— 断电重启一下功放板试试。）

# 第三轮更正（2026-10-23）：B1 那个结论是错的

上面 B1 把"只在有声音时出现的杂音"归因于**变调算法的 5~9 dB 调幅**，这一条
**不适用于用户的实际用法**：用户用的是 **直通档**（`sw[7:6]=00`），而直通档在
`rtl/voice_proc.v` 里就是 `dout <= din`，根本不经过变调算法。

真正的根因是**板子里跑的比特流是过期的**（`spi_mirror_tx.v` 改完 CS̄ 帧同步之后
没有重新综合），导致 STM32 把每个字都当左声道、几乎不刷新 DAC。
完整证据链、前后实测对比、以及"烧录前先比时间戳"的防呆脚本，见：

**`docs/杂音根因_过期比特流_2026-10-23.md`**

B1 里那组数字本身没错（变调档确实有 4.8~8.9 dB 的包络起伏，是算法固有特性），
但它解释的不是用户遇到的那个杂音。
